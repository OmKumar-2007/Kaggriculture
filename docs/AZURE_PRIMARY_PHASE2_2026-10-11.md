# FarmCraft Azure primary, Phase 2 (local preparation only)

Date: 2026-10-11. Branch: `azure-primary-phase2`. No Azure resource or production service was changed in this phase.

## Decision

Use one Azure Container App that serves the built React assets and FastAPI from the same HTTPS origin. `backend/main.py` already serves `/`, SPA routes and versioned assets from `FARMCRAFT_STATIC_DIR`; API endpoints, cookies, CSRF headers and admin routes can remain same-origin. The local Docker smoke test must confirm routing before deployment. Option B, Static Web Apps Free plus Container App API, needs cross-origin credentialed cookies and CORS across many API prefixes. SWA's linked Container Apps API requires the paid Standard plan and only proxies `/api/*`, so it does not fit current routes without a substantial rewrite. Keep Render available as an application fallback, with write traffic gated during failover.

Schema initialization on import must be run only against this empty staging DB; legacy player import stays disabled. Keep historical 16 qualifiers and objects in the old environment. No copy is planned.

## Database traffic and performance

Before this phase, job SSE ran every 2 seconds and the Lab simultaneously polled the full `/jobs/{id}` every 5 seconds, selecting and serializing `SimulationJob.result_json` and `payload_json` even for status changes. The new `get_job_status` selects 13 narrow scalar fields and team username, omitting both JSON columns. SSE and 5-second polling use it; terminal SSE sends one full result for compatibility, while terminal status polling fetches it once. `/jobs/{id}` remains backward compatible. Other transfer candidates remain: team/admin job list result reads, qualification leaderboard aggregation and participant heartbeat writes. No scoring, official attempts or game results were changed. The SQL regression test inspects SELECT statements and rejects the two JSON columns on status reads; compare actual transferred bytes on a future isolated DB before claiming a measured saving.

## 30-team rehearsal sizing

Three references × one seed × two sides × 30 entrants = 180 full games. The previously observed 26–38 seconds/game implies 4,680–6,840 evaluator slot-seconds. To fit 900 seconds, ideal minimum is 6–8 slots; 10 slots leaves overhead for queueing, retries and IO. Two current slots imply ~39–57 minutes before overhead. The current Korean subscription quota (6 regional vCPUs total, 2 already used) cannot be assumed to sustain a 10-slot VM fleet; test per-slot CPU/RAM and request quota increase or use approved cross-region capacity before selecting VM sizes. No 30-team load was launched.

## Failover and rollback

Render remains deployed during staging and is not modified in Phase 2. Azure will become authoritative only after a separately approved cutover. Before switching writes, freeze official submissions, record job/claim state, quiesce worker claims, snapshot database and private objects together, validate staging with synthetic teams, then route clients to one writable stack. On failure, disable Azure writes first, restore a consistent database/object pair to Render's backup environment, reconcile queued jobs and official claims, then route traffic. Returning to Azure reverses that process. A live Render process without an independent current database and object copy is not disaster recovery.

## Approval gates

Separate authorization is required for resource provisioning or PostgreSQL eligibility create attempt (and its paid running time), any VM resize or extra worker, any credential change, any copy of live data, a production load test, a Render/Azure deployment, DNS or traffic cutover, and infrastructure deletion. Before approval, obtain subscription-specific quote for every resource and set alerts/cleanup date. An Azure PostgreSQL feasibility create command would target a **new** resource group and unique server name using `az postgres flexible-server create` with B1ms, 32 GiB and private networking. Stop the server/delete the new group after recording the result only with explicit deletion authorization; PostgreSQL Flexible Server stop does not remove storage charges.
