# Archived full-Azure control-plane design

The active architecture keeps the website and API on Render and uses Azure only for dedicated evaluator VMs. See [hybrid progress](../docs/HYBRID_RENDER_AZURE_PROGRESS.md) and [worker lifecycle](../azure-workers/README.md). `azure/deploy.ps1` now requires the explicit `-LegacyFullAzure` switch; the organizer launcher does not call it. The templates below are preserved for reference and are not part of the hybrid deployment.

The root `START_FARMCRAFT.bat` asks for a mode on every launch. Azure modes share `config/local-profiles/azure-site.json`; Azure plus laptop uses a distinct ignored `azure-laptop.env` and `azure-worker-credentials.json`. Render continues to use its existing `.env`, `credentials.json`, and `render.yaml`. The launcher never copies a worker credential between providers.

## Current readiness

- **Azure plus local evaluator:** the existing outbound HTTPS worker can target an Azure API, with the same job protocol, evaluator version, frozen reference sources, PostgreSQL queue, and scoring path as Render. This path still needs an actual Azure API, PostgreSQL, Redis session service, and Blob container deployed and configured.
- **Full Azure cloud evaluation:** deliberately **disabled**. The server reports `LOCAL` as the active evaluator mode and rejects `AZURE_CLOUD` activation. A cloud runner with validated isolation for untrusted contestant Python has not been built. Selecting the mode never starts an insecure runner or creates paid resources.
- `azure/control-plane.bicep` is a **base-resource preview**, containing a private Blob container, Container Apps environment, and Static Web App. `azure/application.bicep` defines a bounded FastAPI Container App with managed identity and Blob Data Contributor access, supplied with separately approved PostgreSQL, Redis, and versioned image inputs. It does not create PostgreSQL, Redis, an image registry, or evaluator jobs. Neither template has been validated against a live subscription because Azure CLI/login are unavailable in this checkout. `azure/deploy.ps1` shows a what-if preview of the base template and requires `DEPLOY BASE` before provisioning. Do not interpret a successful base deployment as a working application.

## Student setup

1. Install Azure CLI and run `az login` in your own terminal. Select the intended Azure for Students subscription with `az account set --subscription <id>`. Do not paste Microsoft credentials into project files.
2. Launch `START_FARMCRAFT.bat`, choose Azure mode, then **First-Time Setup**. Edit the ignored `config/local-profiles/azure-site.json` and, for laptop mode, `azure-laptop.env`. The setup check prints subscription, region, provider registration states, and `UNKNOWN` for credit/quota values it cannot verify.
3. Check current credit and quota in Azure Cost Management and the subscription Quotas page. Review the bill of materials shown by **Deploy / Update Application** and the Azure what-if output. Provision only after an explicit `DEPLOY BASE` confirmation. This is optional infrastructure preparation, not a completed application deployment.
4. For an Azure API, build a versioned image from `azure/Dockerfile` (Docker context is the repository root) and use `azure/application.bicep`. The Azure image adds Blob SDK dependencies; the existing Render dependency set stays unchanged. The Bicep definition sets `APP_ENV=production`, `QUEUE_BACKEND=postgres`, `STORAGE_BACKEND=azure`, Blob account/container, frontend CORS, and evaluator version. It grants the API managed identity **Storage Blob Data Contributor** on the private container. Supply the PostgreSQL, Redis, and admin secrets through a secure Azure deployment path, such as Key Vault references, never by placing literals in repository files or a shell command line. The API must report all checks healthy at `/ready` before worker registration.
5. Build the Vite frontend with `VITE_API_BASE` set to the Azure API HTTPS URL, deploy `frontend/dist` to Static Web Apps, and set `frontendUrl`/`apiUrl` in the ignored profile. Configure CORS for the actual Static Web Apps origin. Verify secure cross-site session cookies in a browser before opening registration.
6. In the Azure `/admin` portal, create a one-use worker registration token. For Azure plus laptop, rerun setup, register the worker, then choose **Start FarmCraft**. The launcher verifies the API readiness, evaluator version and configuration hash, Docker image, own worker registration, and a fresh backend heartbeat. Do not start a Render worker with the Azure credential.

The Azure API, database, Blob storage, Redis, and Static Web App have **not** been provisioned or tested here. A fully automated Azure application deployment and secure cloud evaluation remain open work. The two Azure modes must use the same Azure deployment and database; no Azure-to-Render data migration is performed.

## Security and cost decision

Contestant agents are arbitrary Python. The current portable runner uses a Docker container with restricted privileges, filesystem, network, CPU, memory, and PID limits. Running that code directly inside a Container Apps Job would put it in the same container context as evaluator credentials and the network path used to submit results. Container Apps' environment boundary alone does not demonstrate isolation of contestant code from those secrets and APIs. [Microsoft's Container Apps guidance](https://learn.microsoft.com/en-us/azure/well-architected/service-guides/azure-container-apps) specifically calls out isolating untrusted code; [Dynamic Sessions](https://learn.microsoft.com/en-us/azure/container-apps/sessions) may be a candidate but requires a separate protocol and security review. A production cloud evaluator must demonstrate a sandbox boundary, secret separation, no direct result forgery, resource limits, restricted egress, and recovery semantics before enabling `AZURE_CLOUD`.

Azure for Students includes limited credit and eligible free quantities, **not unlimited free hosting**. [Microsoft documents](https://learn.microsoft.com/en-us/azure/education-hub/navigate-costs) budgets and credit monitoring, while [Container Apps Jobs](https://learn.microsoft.com/en-us/azure/container-apps/billing) consume billable active resources. Budget alerts do not provide a hard cap. The preflight reports credit as `UNKNOWN` until checked in the portal; no job concurrency or dispatch is enabled by this code.

## Event-day rule

Use Azure plus laptop only after Azure API readiness and worker heartbeat are confirmed. Pause or drain the worker in Admin before shutting down. Tournament attempts with partial games require organizer review after interruption. Do not change an active mode by editing a local profile or database row. Full cloud switching remains unavailable until the isolated cloud runner and its atomic, fenced transition are implemented and tested.
